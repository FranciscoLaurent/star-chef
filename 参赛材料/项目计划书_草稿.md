## 一、项目概述

### 1.1 背景

餐饮行业的厨师职业信息长期依赖熟人引荐，技能水平与师承脉络缺乏可记录、可检索、可验证的承载形式。师承关系是中国烹饪行业最基础、也最隐性的信任机制：一位厨师出自何人门下、属于哪一菜系门派、代际如何延续，通常只在口耳相传中存在，难以进入招聘、评价与协作等正式场景。其结果是，厨师的技艺难以被结构化表达，雇主也缺少除简历与试菜之外的低门槛核验依据。

近年来，大语言模型在非结构化文本结构化方面趋于可用，为上述矛盾提供了新的技术路径：让不擅长文字表达的从业者以口语描述自身经历，由 AI 抽取为规范档案；同时把分散在公开资料中的师承信息整理为可追溯的结构化数据。本作品即在这一背景下，尝试把「师承」从隐性人际关系转化为职业基础设施。

按本届赛事规则，主题为「软件定义世界，创新引领未来」，**不允许自选题目**，须在四个指定赛题中归属其一（AI赋能学习生产力 / AI融入日常 / AI+影像 / AI+健康）；作品须为原创且未参加过其他国家级公开比赛，核心工作、关键组件与主要开发过程须在本次大赛期间完成，并实行匿名评审。**赛题归属（Q-11）与「主要开发过程」界定（Q-05 后半问）尚未落定，见第四章「未决项与待确认事项」。** 本稿不替团队选定赛题，亦不对组委会口径作结论性表述。

> 说明：仓库早期文档中出现的行业规模数量级描述未附独立来源，本稿不予引用，仅作上述定性陈述（**待核实**，见《本稿标注为「待核实」的事实》第 1 条）。

### 1.2 目的

本作品的目标是在区域赛初赛阶段交付一个**可运行、可复核、匿名合规**的厨师职业平台原型，具体为四点：

1. 把师承关系数字化为可记录、可检索、可参与匹配的结构化数据，形成以门派—代际—师徒为骨架的数字师承谱；
2. 提供 AI 求职助手，使不擅长文书表达的厨师以口语描述即可获得规范化求职档案，降低数字工具使用门槛；
3. 提供厨师与雇主的双向推荐，并给出**可解释**的匹配理由，而非仅输出一个分数；
4. 建立一条从公开资料采集、清洗、合并到多端消费的数据管线，保证人物与师承信息「可溯源、宁缺毋滥」，并明确区分真实数据与演示数据。

上述目标共同指向一个边界清晰的产品定位：本作品是**职业信息基础设施的原型验证**，不宣称已具备真实用户规模、合作单位或运营数据；岗位与薪资等用于展示匹配逻辑的数据均在界面中显式标注为演示数据（呼应「应用价值」评分项，见《评分项呼应对照》）。

### 1.3 创新点

**创新点一（题材）：以「师承」而非「简历」作为信任底层。** 现有招聘类产品多以简历字段与评分体系为核心，本作品把行业中最具约束力、却最难被系统表达的师承关系作为一等数据建模对象：合并层为 1537 条厨师记录与 9 个门派，Web 消费层为 1415 条记录（1238 条真实档案 + 177 条派生记录，`meta.total=1238`），并携带 `apprenticeMap` 师徒反查表与代际 `gen` 字段。垂直、具体且有真实数据支撑，避免了题材泛化（呼应「创新性—题材」）。

**创新点二（解决方案）：零编造约束下的 AI 结构化 + 可解释匹配。** AI 求职助手的抽取提示词明确要求「只提取明确说出的信息，严禁编造、推测或用行业默认值填充」，输出后由本地逻辑复核档案完整度（按姓名 / 菜系 / 从业年限 / 求职意向四项，每缺一项扣 25 分），防止模型虚增字段；模型不可用时回退到基于规则的本地解析，保证页面始终可用。招聘匹配采用四维加权口径（菜系 40 + 师门 25 + 地域 20 + 薪资 15 = 100），逐维给出命中理由，并支持「库外自由档案」——厨师不必已存在于厨师库，随手填写即可匹配（呼应「创新性—解决方案」「软件技术—程序复杂度」）。

**创新点三（体验设计）：面向低数字素养人群的界面与全端适配。** 师承谱采用古籍宗谱式三栏版式（选门派 / 看谱系 / 读档案），视觉沿用复古纸纹与报刊排版；动效由 GSAP 驱动并遵循 `prefers-reduced-motion`；移动端通过 `viewport` 声明、12 档宽度断点（520–1100px 区间）、汉堡菜单与抽屉式详情实现响应式布局，使不擅长复杂操作的使用者也能完成检索与浏览（呼应「创新性—体验设计」）。

**创新点四（工程诚实性）：数据边界显式标注。** 岗位、薪资与期望薪资推算在界面与源码中均标注为「演示数据」，真实厨师档案则标注来源；数据加载与 AI 调用均设有错误边界与降级路径。这一处理使作品在评审环境中可被逐项复核，不以模拟数据冒充实际运行效果（呼应「应用价值」「软件工程质量—软件质量」）。

## 二、技术方案

### 2.1 总体架构

主交付物 `web/` 为纯前端 SPA，采用分层结构，无自建后端服务：

| 层 | 组成 | 职责 |
| --- | --- | --- |
| 表现层 | React 19 + React Router 7（`BrowserRouter`）+ 6 个业务路由 | 页面渲染、路由、交互状态 |
| 数据层 | `web/public/data/chefs.json`（运行时 `fetch`）+ `useData` hook + `types.ts` | 静态数据加载、全局缓存、类型约束 |
| AI 能力层 | `web/src/lib/ai.ts` 统一封装 + `/api/deepseek` 代理 / 直连双模式 | SSE 流式调用、结果解析、失败降级 |
| 离线数据管线 | `scripts/` + `data/` | 采集、清洗、合并、索引、多端产物生成 |
| 附属消费端 | `miniprogram/`、`lineage_demo/` | 小程序形态、交互原型（见 2.4） |

关键设计取舍：**前端与数据解耦**。页面不内置数据，而是在运行时 `fetch('/data/chefs.json')`，由模块级单例缓存，替换数据文件无需重新构建；**AI 与业务解耦**。所有模型调用收敛到 `ai.ts`，业务页面只依赖 `extractResume` / `callDeepSeek(explainPrompt(...))` 等语义接口，并各自保留本地降级实现。技术栈版本为 Vite 8.3.x、React 19.3.x、TypeScript 7.0.x（`~7.0.2`）、react-router-dom 7.18.x、GSAP 3.15.x（呼应「软件技术—架构」）。

### 2.2 功能概述

SPA 由 6 个业务路由加 1 个兜底路由组成（`/`、`/lineage`、`/chef/:id`、`/jobs`、`/assistant`、`/community`、`*` → 首页），对应六类功能：

1. **首页**：作品定位、数字师承谱入口、面孔墙与数据统计；
2. **数字师承谱（`/lineage`）**：按门派 / 代际浏览师承链条，节点区分本人、师承上游与弟子，支持跳转详情；
3. **厨师档案（`/chef/:id`）**：个人档案、师承链条、来源链接、拿手菜、肖像占位与钢印样式；
4. **智能招聘匹配（`/jobs`）**：岗位筛选、四维匹配度拆解、厨师侧自由填写表单、雇主侧按从业年限筛选、AI 一句话匹配理由；
5. **AI 求职助手（`/assistant`）**：口语描述 → 严格 JSON 抽取 → 结构化求职档案，流式输出、完整度提示、DeepSeek 设置面板（输入 Key、选择代理/直连模式）；
6. **厨艺社区（`/community`）**：帖子列表、详情、评论与发帖（本地状态，用于展示社区形态）。

功能之间以「同一份厨师数据」串联：师承谱、档案、匹配、助手共享 `chefs.json`，避免多份数据副本造成的口径漂移。功能覆盖检索、图结构浏览、算法匹配、AI 生成与表单交互，具有一定程序复杂度（呼应「软件技术—程序复杂度」）。

### 2.3 关键技术

**（1）真实数据管线与师承建模。** 管线自 `scripts/` 的采集脚本（`cyxh-crawler*.js`、`cswzg-*.js`、`list-crawler.js`、`cmccx-crawler.js` 等）起始，产出 `data/` 下多来源 JSON；由唯一合并入口 `data/_merge.js` 完成去重、菜系归一化（`CUISINE_NORMALIZE` 映射）与师承关系注入，生成 `data/chefs-merged.json`（1537 条 chefs / 9 门派）；再经 `_slim.json`、`_slim-pinyin.json` 逐级瘦身，由生成器分发到 `web/public/data/chefs.json`、`miniprogram/data/*.js` 与 `lineage_demo/demo-D5~D7.html`。师承关系由 `chefs[].master` / `masters` 等字段承载，Web 侧另建 `apprenticeMap` 反查表与 `gen` 代际字段，并记录推断边数量（`meta.inferredEdges=189`）。约定「改数据只改来源 JSON 或合并脚本，然后重跑生成器，不手改产物」（呼应「软件技术—技术深度」「软件工程质量—软件过程」）。

**（2）拼音与多字段加权检索。** 基于 `data/_pinyin/kMandarin_8105.txt` 生成姓名拼音索引；`web/src/lib/search.ts` 一次构建索引、多次查询，按「精确姓名 100 > 姓名子串 80 > 拼音全拼 70 / 首字母 65 / 拼音子串 60 > 菜系 50 > 拿手菜·称号·职位 40」加权评分并去重取前 30 条。索引覆盖中文、拼音全拼与首字母，适配不熟悉汉字输入或只记得读音的使用场景（呼应「软件技术—技术深度」「程序性能」）。

**（3）AI 流式调用与降级。** `web/src/lib/ai.ts` 统一以 SSE 流式调用 `deepseek-chat`：手动解析 `data:` 帧、累积增量、回调 `onToken` 逐字渲染；对模型输出采用「去 ``` 围栏 + 正则截取」的容错 JSON 解析，并由本地逻辑复核完整度。仓库不含任何明文 API Key 与 `.env` 配置文件：Key 由使用者在页面输入并存于浏览器本地存储，提供 `/api/deepseek` 开发代理（`vite.config.ts`，规避 CORS 并关闭代理缓冲以保证流式）与直连 `https://api.deepseek.com` 两种模式。无 Key 或网络失败时，求职助手回退 `demoExtract` 规则解析、匹配理由回退 `demoExplain` 本地生成，页面始终有完整输出（呼应「软件工程质量—软件质量」）。

> 关于 AI 业务调用点的数量：Web 版现状收敛为**两类页面业务调用**（求职档案抽取、招聘匹配理由生成），共用 `ai.ts` 统一封装；仓库早期开发说明记载旧单文件版本曾含 4 处独立 prompt，与 Web 重构后现状不一致（**待核实**，见《本稿标注为「待核实」的事实》第 2 条）。本稿按代码写实，不沿用「4 处」表述。

**（4）性能与稳定性设计。** `useData.ts` 采用模块级单例缓存与 `fetch` try/catch，加载失败向上返回 `error` 而不使页面崩溃；`jobs.ts` 的匹配与 `search.ts` 的检索均为纯函数、无网络往返；数据经 `_slim` 瘦身与拼音索引预处理，控制首屏解析开销；样式侧 12 档宽度断点配合 `prefers-reduced-motion` 与 `hover:none` 适配不同设备与动效偏好（呼应「软件技术—程序性能」）。

### 2.4 其他技术

**（1）微信小程序（附属形态，按 A1 口径已从手机端展示范围下线）。** `miniprogram/` 为微信原生小程序，含 5 个页面（`home` / `lineage` / `jobs` / `assistant` / `community`）与自定义 tabBar（`app.json` 中 `tabBar.custom=true`），使用 `touristappid` 游客 AppID；其 AI 能力当前为**本地规则 mock**（`services/ai.js` 明确「当前仅实现 mock 引擎」，预留将来经云函数代理接入真实模型），数据由 `scripts/build-mp-data.js` / `build-mp-mock.js` 生成到 `miniprogram/data/`。该形态属附属、待裁剪部分，**不纳入本轮主交付与手机端展示范围**。

**（2）交互原型与视觉工程。** `lineage_demo/` 保留师承谱交互方案原型（A、B、C、D1–D4 及由脚本生成的 D5–D7），记录了从家谱、网络图到时间轴等方案的取舍过程；`web/src/styles/design-system.css`、`tokens.css`、`app-shell.css` 构成设计令牌与壳层样式，`motion.ts` 封装 GSAP 动效。

**（3）工程质量现状。** 采用 TypeScript 类型约束、`oxlint` 静态检查与「先改生成器、再重跑产物」的协作约定；**当前仓库未配置任何测试框架**（`web/package.json` 无 vitest / jest / playwright 等依赖），该项列为待整改风险（见 4.4）。

## 三、项目计划

### 3.1 可行性分析

**技术可行性。** 主体功能已在仓库中落地为可构建的 SPA（Vite 构建脚本 `tsc -b && vite build`），数据管线、检索、匹配、AI 调用与响应式布局均有源码可查，技术栈为成熟稳定版本，无待攻克的未知技术环节。剩余工作以整改与材料合规为主，而非从零实现。

**资源可行性。** 运行不依赖自建服务器与数据库：数据为静态 JSON，AI 调用由使用者提供 Key，部署形态为静态站点，运行与评审成本低，适合区域赛初赛的评审环境。

**进度可行性。** 主体代码已经存在，排期按「合规复核 → 口径确认 → 工程整改 → 材料定稿 → 提交」组织，不依赖新增核心模块；具体日期由团队据实填写（见 3.2、4.3）。

**合规可行性（须重点复核）。** 匿名评审要求所有材料不得出现学校信息与成员姓名，本稿已按此约束起草并保留占位；作品原创性与「未参加过其他国家级公开比赛」须由团队据实声明（**待核实**，见第 3 条）；「主要开发过程须在本次大赛期间完成」的界定待组委会书面答疑（Q-05 后半问，**待核实**）。上述三项在正式提交前必须闭环，否则存在形式审查风险。

**风险与应对。** 已识别的工程与合规风险集中列于 4.4，其中「三套数据口径并存」「旧赛事标识残留」「定宽样式残留」「无测试框架」均有明确的整改动作与验收方式，可在排期 S2 阶段集中处理（呼应「软件工程质量—软件过程 / 软件质量」「软件技术—架构」）。
